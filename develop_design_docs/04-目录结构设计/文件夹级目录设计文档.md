# 文件夹级目录设计文档

## 1 文档说明
**说明**：本文档详细描述智能烟感系统的项目目录结构，包含后端和前端两个部分的文件夹级目录设计，确保项目结构清晰、模块划分合理、易于维护和扩展。

## 2 通用规范要求
- **分层原则**：按技术分层（MVC架构），模块划分合理，目录结构清晰
- **扩展适配**：新增功能优先扩展子目录，不修改核心分层；第三方依赖、合规相关（加密/权限）单独分层，与业务解耦
- **命名规范**：文件夹名称为小写英文，采用"功能关键词"命名（如"security"、"thirdparty"），避免模糊表述
- **包名策略**：
  - `com.ruoyi`：若依框架基础代码，保持不变
  - `com.iot`：IoT业务代码，所有传感器相关业务功能使用此包名
  - 新开发的IoT业务功能必须使用 `com.iot` 包名，确保符合架构设计要求

### 3.2 关键文件夹功能说明

| 文件夹 | 核心功能 | 设计原则体现 | 适配要求 |
| :--- | :--- | :--- | :--- |
| api/controller | 暴露外部访问接口，负责请求接收、参数校验、响应格式化，不包含业务逻辑 | 单一职责、高内聚 | 与业务层通过Service接口依赖，禁止直接操作数据源 |
| api/dto | 定义接口层的入参和出参对象，负责数据校验和格式转换 | 单一职责 | 按业务场景划分，避免DTO混乱 |
| service | 业务层接口定义抽象逻辑，定义核心业务流程 | 依赖倒置、开闭原则 | 新增业务逻辑时，新增接口和实现类，不修改原有接口 |
| service/impl | 业务层实现类，落地具体业务流程 | 依赖倒置、开闭原则 | 实现类依赖接口，不依赖具体数据源实现 |
| service/vo | 定义业务层的视图对象，用于返回给前端的数据结构 | 单一职责 | 按业务场景划分，避免VO混乱 |
| mapper/entity | 定义数据库实体类，映射数据库表结构 | 单一职责 | 实体类与数据库表一一对应 |
| mapper/xml | MyBatis映射文件，定义SQL语句和结果映射 | 单一职责 | 按实体类划分，一个实体对应一个Mapper接口和XML文件 |
| protocol/adapter | 协议适配器，将不同协议的传感器数据转换为统一格式 | 开闭原则、依赖倒置 | 新增协议支持时，新增适配器实现类，不修改原有代码 |
| protocol/codec | 协议编解码器，处理协议数据的编码和解码 | 单一职责 | 按协议类型划分，一个协议对应一个编解码器 |
| protocol/model | 协议数据模型，定义协议数据的结构 | 单一职责 | 按协议类型划分，避免模型混乱 |
| netty/handler | Netty网络处理器，处理传感器数据的接收和发送 | 单一职责、高内聚 | 按功能划分，如数据接收处理器、心跳处理器等 |
| netty/server | Netty服务器，负责启动和管理Netty服务 | 单一职责 | 封装Netty服务器的启动、停止等操作 |
| alarm/rule | 报警规则定义和管理，包括规则配置、规则匹配等 | 单一职责、开闭原则 | 支持规则扩展，新增规则类型时只需扩展规则类 |
| alarm/processor | 报警处理器，负责报警检测和处理 | 单一职责、高内聚 | 与报警规则解耦，通过接口依赖 |
| notification/channel | 通知渠道实现，包括短信、语音、APP推送等 | 开闭原则、依赖倒置 | 新增通知渠道时，新增渠道实现类，不修改原有代码 |
| notification/template | 通知模板管理，包括模板定义、变量替换等 | 单一职责 | 按通知类型划分，支持模板扩展 |
| common/constant | 常量定义，包括业务常量、系统常量等 | 单一职责 | 按模块划分，避免常量混乱 |
| common/exception | 异常处理，包括自定义异常、全局异常拦截等 | 单一职责、高内聚 | 统一异常处理机制，与业务逻辑解耦 |
| common/utils | 工具类，包括日期、字符串、JSON等工具 | 单一职责 | 按功能划分，避免工具类职责混乱 |
| common/validator | 数据验证，包括参数校验、业务规则校验等 | 单一职责 | 与业务逻辑解耦，可复用 |
| config/redis | Redis配置，包括连接池、序列化等配置 | 单一职责 | 与业务逻辑解耦，统一管理Redis配置 |
| config/mysql | MySQL配置，包括数据源、事务等配置 | 单一职责 | 与业务逻辑解耦，统一管理MySQL配置 |
| config/netty | Netty配置，包括服务器参数、线程池等配置 | 单一职责 | 与业务逻辑解耦，统一管理Netty配置 |

## 5 设计原则落地说明

### 5.1 高内聚低耦合
- **模块职责划分清晰**：每个文件夹只负责一个明确的职责，如`api/controller`只负责接口暴露，`service`只负责业务逻辑
- **模块间通过接口通信**：`api/controller`通过`service`接口调用业务逻辑，不直接操作数据源
- **避免模块间直接依赖**：业务模块通过接口依赖，如`alarm/processor`依赖`NotificationService`接口而非具体实现

### 5.2 开闭原则
- **新功能通过扩展实现**：新增协议支持时，在`protocol/adapter`目录下新增适配器实现类，不修改原有代码
- **不修改原有代码**：新增通知渠道时，在`notification/channel`目录下新增渠道实现类，不修改原有代码
- **使用接口或抽象类**：业务层通过接口定义，实现类在`service/impl`目录下，支持扩展

### 5.3 依赖倒置原则
- **高层模块依赖抽象**：`api/controller`依赖`service`接口，不依赖具体实现
- **抽象不依赖具体实现**：`service`接口定义抽象逻辑，不依赖具体数据源实现
- **具体实现依赖抽象**：`service/impl`实现类依赖`service`接口和`mapper`接口

### 5.4 单一职责原则
- **类/函数职责单一**：每个文件夹只负责一个明确的职责，如`protocol/adapter`只负责协议适配
- **避免职责扩散**：工具类放在`common/utils`目录，业务逻辑放在`service`目录，避免职责混乱
- **一个类/函数只做一件事**：每个文件只实现一个核心功能，如`DeviceController`只负责设备管理接口
