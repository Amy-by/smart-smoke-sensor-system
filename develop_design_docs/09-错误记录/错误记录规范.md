# 错误记录规范

## 1. 目的

本规范旨在建立统一的错误记录标准，确保开发团队能够高效地记录、跟踪和解决系统开发过程中遇到的各种错误和问题，提高开发效率和代码质量。

## 2. 适用范围

本规范适用于智能烟感系统开发过程中所有阶段（需求分析、设计、开发、测试、部署、维护）遇到的错误和问题。

## 3. 错误分类

### 3.1 按技术领域分类

- **后端错误（BE）**：后端服务、API接口、数据库等相关错误
  - **业务逻辑错误**：业务规则实现、状态管理、流程控制等错误
  - **数据访问错误**：数据库连接、SQL语句、事务管理等错误
  - **协议编解码错误**：各种通信协议的编码、解码实现错误
  - **依赖管理错误**：第三方库依赖、版本冲突、缺失依赖等错误
  - **测试框架错误**：测试用例编写、测试环境配置等错误
  - **其他后端错误**：无法归类到上述子类的其他后端错误

- **前端错误（FE）**：UI界面、前端组件、数据交互等相关错误
  - **界面展示错误**：页面布局、样式、响应式设计等错误
  - **交互逻辑错误**：用户操作响应、表单验证、状态管理等错误
  - **数据处理错误**：数据格式化、转换、验证等错误
  - **API调用错误**：与后端API交互的错误
  - **其他前端错误**：无法归类到上述子类的其他前端错误

- **系统集成错误（SI）**：系统间集成、第三方服务对接等相关错误
  - **内部系统集成错误**：系统内部模块间的集成错误
  - **第三方服务集成错误**：与外部系统或API的集成错误
  - **通信协议错误**：系统间通信协议的实现和使用错误
  - **数据交换错误**：系统间数据格式、传输等错误

- **部署运维错误（DO）**：系统部署、环境配置、性能监控等相关错误
  - **环境配置错误**：开发、测试、生产环境的配置错误
  - **部署脚本错误**：自动化部署脚本的错误
  - **性能问题**：系统性能、响应时间、资源占用等问题
  - **监控告警错误**：系统监控、日志记录、告警配置等错误

### 3.2 按严重程度分类

- **致命错误（Critical）**：导致系统崩溃、数据丢失或核心功能完全不可用的错误
- **严重错误（High）**：导致重要功能不可用或影响大量用户的错误
- **中等错误（Medium）**：导致部分功能不可用或影响少数用户的错误
- **轻微错误（Low）**：不影响系统功能，仅影响用户体验或代码质量的错误

## 4. 错误记录格式

每个错误记录必须包含以下五个主要部分：

### 4.1 错误描述

- **错误标题**：简洁明了地描述错误的核心问题
- **错误现象**：详细描述错误发生时的具体表现
- **发生环境**：记录错误发生的系统环境信息
  - 操作系统版本
  - 浏览器类型和版本（前端错误）
  - 设备型号和操作系统（移动应用错误）
  - 网络环境
  - 系统版本号
- **复现步骤**：详细列出能够复现错误的操作步骤
  ```
  1. 打开系统登录页面
  2. 输入正确的用户名和错误的密码
  3. 点击登录按钮
  4. 观察系统反应
  ```
- **错误截图**：如有必要，添加错误发生时的截图或录屏

### 4.2 错误分析

- **错误定位**：确定错误发生的具体位置
  - 文件路径
  - 函数/方法名
  - 行号
- **错误日志**：记录相关的错误日志信息
- **可能原因**：分析可能导致错误的原因
  - 代码逻辑错误
  - 数据格式错误
  - 环境配置问题
  - 依赖库问题
  - 网络问题
- **影响范围**：评估错误对系统功能的影响范围
  - 影响的功能模块
  - 影响的用户群体
  - 影响的业务流程

### 4.3 解决方案

- **解决思路**：描述解决错误的整体思路和方法
- **具体步骤**：详细列出实施解决方案的步骤
- **代码修改**：记录相关的代码修改内容
  ```javascript
  // 错误代码
  function calculateTotal(price, quantity) {
    return price * quantity;
  }
  
  // 修复后的代码
  function calculateTotal(price, quantity) {
    if (typeof price !== 'number' || typeof quantity !== 'number') {
      return 0;
    }
    return price * quantity;
  }
  ```
- **相关依赖**：记录需要更新或修改的依赖库

### 4.4 验证结果

- **验证方法**：描述验证解决方案有效性的方法
- **验证环境**：记录验证的系统环境信息
- **验证结果**：详细描述验证结果
  - 错误是否复现
  - 功能是否正常工作
  - 性能是否受影响
  - 其他相关功能是否正常
- **测试截图**：如有必要，添加验证后的截图或录屏

### 4.5 相关信息

- **记录人**：记录错误的人员姓名
- **记录时间**：错误记录的时间（格式：YYYY-MM-DD HH:mm:ss）
- **解决人**：解决错误的人员姓名
- **解决时间**：错误解决的时间（格式：YYYY-MM-DD HH:mm:ss）
- **严重程度**：错误的严重程度（致命/严重/中等/轻微）
- **关联任务**：相关的开发任务或需求编号
- **关联文档**：相关的设计文档或规范
- **备注**：其他需要说明的信息

## 6. 文件命名规范

错误记录文件的命名应遵循以下格式：

```
[分类缩写]-[四位数字编号]-[简要描述].md
```

### 6.1 分类缩写

使用以下缩写表示错误分类：

- **后端错误**：BE
- **前端错误**：FE
- **系统集成错误**：SI
- **部署运维错误**：DO

### 6.2 错误编号

- **全局唯一编号**：整个项目中所有错误记录使用连续的四位数字编号，从0001开始递增
- **编号分配**：由记录人在创建错误记录时，根据当前已有的最大编号自动递增分配
- **避免重复**：确保在整个项目中错误编号唯一，不与其他错误记录重复

### 6.3 简要描述

- 使用中文描述错误的核心问题
- 字数控制在15个汉字以内
- 避免使用特殊字符和空格，使用连字符(-)分隔多个词语
- 描述应简洁明了，能够快速识别错误类型

### 6.4 示例

- `BE-0001-用户状态码定义错误.md`
- `BE-0002-数据库初始化缺失.md`
- `BE-0003-Zigbee协议分隔符转义问题.md`
- `FE-0001-登录页面样式异常.md`
- `SI-0001-第三方API调用失败.md`
- `DO-0001-服务器部署失败.md`

## 7. 记录流程

1. **发现错误**：开发人员在开发、测试或用户反馈中发现错误
2. **初步评估**：评估错误的严重程度、影响范围和技术领域
3. **确定分类**：根据错误的技术领域和具体类型，确定其所属的分类和子分类
4. **分配编号**：根据当前已有的最大错误编号，分配一个新的唯一编号
5. **创建记录**：在相应的分类目录下创建错误记录文件，使用规范的命名格式
6. **填写信息**：按照错误记录格式填写完整的错误信息
7. **分配处理**：将错误分配给相关开发人员处理
8. **实施修复**：开发人员实施解决方案
9. **更新记录**：修复完成后，更新错误记录中的解决方案和验证结果
10. **关闭记录**：验证通过后，关闭错误记录

## 8. 编号管理

为了确保错误编号的唯一性和连续性，建议使用以下方法管理编号：

1. 在`README.md`文件中维护当前最新的错误编号
2. 创建错误记录时，先查看README.md获取最新编号，然后递增1
3. 创建错误记录后，及时更新README.md中的最新编号

### 8.1 README.md格式示例

```markdown
# 错误记录目录

## 最新错误编号

- 后端错误(BE)：0004
- 前端错误(FE)：0000
- 系统集成错误(SI)：0000
- 部署运维错误(DO)：0000

## 错误记录列表

| 编号 | 错误类型 | 错误描述 | 文件路径 |
|------|----------|----------|----------|
| BE-0001 | 业务逻辑错误 | 用户状态码定义错误 | 后端错误/业务逻辑错误/BE-0001-用户状态码定义错误.md |

## 9. 管理与维护

1. **定期回顾**：每周进行一次错误记录回顾，总结经验教训，避免重复犯同样的错误
2. **统计分析**：每月对错误记录进行统计分析，识别常见问题和改进方向
   - 按错误类型统计出现频率
   - 按模块统计错误分布
   - 分析错误解决时间和效率
3. **归档管理**：
   - 每季度对已解决的错误记录进行归档
   - 归档时保持原有的分类结构
   - 更新README.md中的归档信息
4. **规范更新**：根据实际使用情况，每半年更新一次本规范，确保其适用性和有效性

### 10.2 错误严重程度评估表

| 严重程度 | 定义 | 示例 |
|----------|------|------|
| 致命错误（Critical） | 导致系统崩溃、数据丢失或核心功能完全不可用的错误 | 系统无法启动、数据库连接失败、核心业务流程中断 |
| 严重错误（High） | 导致重要功能不可用或影响大量用户的错误 | 主要功能模块无法使用、API接口返回错误、数据计算错误 |
| 中等错误（Medium） | 导致部分功能不可用或影响少数用户的错误 | 次要功能异常、UI展示问题、非核心流程错误 |
| 轻微错误（Low） | 不影响系统功能，仅影响用户体验或代码质量的错误 | 拼写错误、代码格式问题、性能优化建议 |

```
发现错误 → 初步评估 → 创建错误记录 → 分配处理 → 实施修复 → 验证修复 → 更新记录 → 关闭记录
```
