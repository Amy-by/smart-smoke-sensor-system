# 通用版 - 软件架构设计需求规范文档（无绑定具体业务/技术栈）
## 核心设计原则（全局约束）
1. 模块间高内聚低耦合：功能相关模块聚合，模块间依赖最小化，通过接口解耦；
2. 开闭原则：新增功能通过扩展实现，不修改原有核心代码；
3. 依赖倒置原则：高层模块依赖抽象（接口/抽象类），不依赖具体实现；
4. 单一职责原则：一个模块/文件/函数只承担一种核心职责，避免功能冗余。

## 一、第一项工作：功能树细化（中粒度通用模板）
### 1. 通用规范要求
- 层级结构：业务域 → 子场景 → 功能点（严格3层，适配多数项目；小型项目可简化为2层，超大型可扩展为4层）；

## 二、第二项工作：文件夹级目录设计（通用技术分层）
### 1. 通用规范要求
- 分层原则：按纯技术分层（适配多数技术栈），架构师可根据技术栈调整目录名称（如Java用「repository」，Go用「dao」）；
- 扩展适配：新增功能优先扩展子目录，不修改核心分层；第三方依赖、合规相关（加密/权限）单独分层，与业务解耦；
- 命名规范：文件夹名称为小写英文，采用“功能关键词”命名（如「security」「thirdparty」），避免模糊表述。

### 2. 通用目录树（后端+前端，架构师适配技术栈）
#### （1）通用后端目录树
```

│   ├── main/
│   │   ├── [框架核心目录]/  # 框架根目录（如Java：com/xxx；Go：xxx/）
│   │   │   ├── api/        # 接口层（接收请求、参数校验、响应封装）
│   │   │   ├── service/    # 业务层（核心逻辑，接口+实现）
│   │   │   │   └── impl/   # 业务实现层（落地逻辑，依赖倒置）
│   │   │   ├── data/       # 数据访问层（操作数据库/缓存，解耦数据源）
│   │   │   ├── model/      # 数据模型层（实体/传输对象/展示对象）
│   │   │   │   ├── entity/ # 存储实体（映射数据源结构）
│   │   │   │   ├── dto/    # 入参/出参传输对象

### 3. 关键文件夹通用功能说明
#### （1）通用后端关键文件夹
| 文件夹         | 核心功能                                                                 | 设计原则体现                | 适配要求                          |

## 三、第三项工作：文件级目录设计（通用单一功能模板）
### 1. 通用规范要求
- 单一功能原则：一个文件仅实现一个核心功能（如“用户注册入参DTO”单独建文件，不合并）；
- 命名规范：后端（大驼峰，如UserRegisterDTO.[后缀]）、前端（小驼峰+类型后缀，如userRegister.dto.[后缀]）；
- 分层对齐：文件目录与文件夹分层严格对齐，文件名明确体现功能（避免“Util.[后缀]”等模糊命名）。

### 2. 通用文件目录树（后端+前端核心目录）
#### （1）通用后端核心文件目录树
```
backend/src/main/[框架核心目录]/
├── api/
│   ├── [Business1]Api.[后缀]  # 业务1接口（如UserApi.java）
│   ├── [Business2]Api.[后缀]  # 业务2接口（如OrderApi.java）
│   └── [Support]Api.[后缀]    # 支撑域接口（如SystemApi.java）
├── service/
│   ├── [Business1]Service.[后缀]  # 业务1业务接口
│   ├── [Business2]Service.[后缀]  # 业务2业务接口
│   └── impl/

## 四、第四项工作：函数级设计（通用核心函数模板）
### 1. 通用规范要求
- 覆盖范围：核心业务函数（如创建/查询/更新业务数据）+ 公共工具函数（如加密/日期/请求封装）；
- 说明要素：核心功能、输入参数（名称/类型/含义）、输出参数（类型/含义/异常）、实现逻辑、依赖模块、异常场景、性能注意事项；
- 命名规范：后端（动词+名词，如createUser）、前端（小驼峰+动词+名词，如createUser），避免模糊命名（如doSomething）。

### 2. 通用函数目录树（核心业务+公共工具）
#### （1）通用后端核心函数目录树
```
[Business1]ServiceImpl.[后缀]/
├── create[Business1]([Business1]CreateDTO dto)  # 业务1创建（核心业务函数）
├── query[Business1]List([Business1]QueryDTO dto)# 业务1列表查询（核心业务函数）
├── update[Business1]([Business1]UpdateDTO dto)  # 业务1更新（核心业务函数）
└── delete[Business1](IDType id)                 # 业务1删除（核心业务函数）

[Algorithm]CryptoUtil.[后缀]/
├── encrypt(String plaintext)  # 加密（公共工具函数）
└── decrypt(String ciphertext) # 解密（公共工具函数）

[Thirdparty]Client.[后缀]/
├── send[Service]([Service]Param param)  # 第三方服务调用（核心业务函数）
```

#### （2）通用前端核心函数目录树
```
[business1]Api.[后缀]/
├── create[Business1](param: [Business1]CreateParam)  # 业务1创建请求（核心函数）
├── get[Business1]List(param: [Business1]QueryParam)  # 业务1列表请求（核心函数）
└── update[Business1](param: [Business1]UpdateParam)  # 业务1更新请求（核心函数）

request.[后缀]/
├── request<T>(config: RequestConfig)  # 统一请求封装（公共工具函数）

[algorithm]Crypto.[后缀]/
├── encrypt(plaintext: string)  # 加密（公共工具函数）
└── decrypt(ciphertext: string) # 解密（公共工具函数）
```

## 五、核心设计原则通用落地指引
| 设计原则       | 通用落地要求                                                                 | 通用示例                                  |
|----------------|------------------------------------------------------------------------------|-------------------------------------------|
| 高内聚低耦合   | 1. 业务逻辑与非业务逻辑（加密/权限）解耦，独立分层；<br>2. 第三方依赖统一封装，不侵入核心业务；<br>3. 模块/文件/函数仅包含相关功能，避免跨职责 | 加密功能放在crypto目录，业务层调用加密工具，不直接写加密逻辑 |
| 开闭原则       | 1. 新增业务功能→扩展实现类/文件，不修改原有核心代码；<br>2. 新增第三方服务→扩展thirdparty子目录；<br>3. 新增规则→扩展配置/工具类 | 新增支付方式→新增PayServiceImpl实现类，不修改原有支付逻辑 |
| 依赖倒置原则   | 1. 高层模块（api层）依赖抽象（service接口），不依赖具体实现；<br>2. 业务层依赖数据层接口，不依赖具体数据源；<br>3. 抽象与实现分离 | api层注入service接口，而非impl实现类；数据层接口可适配MySQL/Redis |
| 单一职责原则   | 1. 一个文件一个功能（如创建DTO与查询DTO分开）；<br>2. 一个函数一个场景（如创建与查询分开）；<br>3. 一个模块一个核心职责（如security仅管权限） | 用户创建入参（UserCreateDTO）与查询入参（UserQueryDTO）分文件 |

## 六、通用交付物清单（架构师需输出）
1. 「功能树细化文档.md」：通用模板填充项目实际业务域、子场景、功能点，含更改记录；
2. 「文件夹级目录设计文档.md」：通用目录树适配项目技术栈，含关键文件夹说明、更改记录；
3. 「文件级目录设计文档.md」：通用文件目录树填充项目实际文件，含关键文件说明、更改记录；
4. 「核心函数设计文档.md」：通用函数模板填充项目实际核心函数，含完整说明、更改记录；
5. 「设计原则落地指引.md」：基于通用指引，补充项目特有的落地示例。

### 交付物通用规范
- 文档格式：统一Markdown，文件名按上述清单命名；
- 版本管理：与代码同仓管理，存放于「docs/design/」目录；
- 更改记录：按迭代版本更新，明确“改了什么、为什么改、影响什么”；
- 一致性：文档与代码结构保持一致，避免“文档与代码脱节”。

## 总结
本通用版文档剥离了具体业务和技术栈绑定，仅提供「结构规范+模板框架+设计原则」，架构师可直接基于此：
1. 填充项目实际信息（业务域、技术栈、特殊约束）；
2. 适配具体需求文件，细化功能树、目录树、文件和函数；
3. 确保设计符合四大核心原则，同时兼顾协作与可维护性。

文档逻辑从宏观（功能树）到微观（函数），层层递进，架构师无需重新搭建框架，仅需按模板填充具体内容，即可快速输出符合要求的架构设计文档。
