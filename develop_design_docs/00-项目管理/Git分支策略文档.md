# Git分支策略文档

## 一、文档说明

目的：规范智能烟感系统开发过程中的Git分支管理，确保团队协作高效、代码质量可控、版本发布稳定。

适用范围：所有参与智能烟感系统开发的团队成员。

## 二、分支模型

采用Git Flow分支管理模型，主要包含以下几类分支：

### 1. 主分支（长期存在）

- **master分支**
  - 功能：存储正式发布的版本，确保随时可发布
  - 权限：受保护分支，仅允许通过Pull Request合并
  - 命名：`master`
  - 特点：代码稳定，可直接部署生产环境

- **develop分支**
  - 功能：日常开发的集成分支，包含所有已完成的功能
  - 权限：受保护分支，仅允许通过Pull Request合并
  - 命名：`develop`
  - 特点：代码相对稳定，可用于测试环境部署

### 2. 辅助分支（临时存在）

- **feature分支**
  - 功能：开发新功能或修复bug
  - 来源：从`develop`分支检出
  - 合并：完成后合并回`develop`分支
  - 命名：`feature/功能名称`（如：`feature/sensor-alarm`）

- **release分支**
  - 功能：准备发布新版本
  - 来源：从`develop`分支检出
  - 合并：完成后同时合并回`develop`和`master`分支
  - 命名：`release/版本号`（如：`release/v1.0.0`）

- **hotfix分支**
  - 功能：修复生产环境紧急问题
  - 来源：从`master`分支检出
  - 合并：完成后同时合并回`develop`和`master`分支
  - 命名：`hotfix/问题描述`（如：`hotfix/login-error`）

## 三、分支操作规范

### 1. 分支创建

- 所有新功能开发必须从`develop`分支创建`feature`分支
- 版本发布前创建`release`分支进行预发布准备
- 生产环境问题修复必须从`master`分支创建`hotfix`分支

### 2. 代码提交

- 提交频率：每个功能点或修复完成后及时提交
- 提交信息：使用清晰、描述性的提交信息
  - 格式：`类型：简短描述`
  - 类型：feat（新功能）、fix（修复bug）、docs（文档）、style（代码风格）、refactor（重构）、test（测试）、chore（构建/工具）
  - 示例：`feat: add sensor alarm notification function`

### 3. 代码合并

- 所有分支合并必须通过Pull Request流程
- Pull Request必须经过至少1名团队成员代码审查
- 合并前必须确保所有测试通过
- 禁止使用`--force`参数强制推送

### 4. 分支删除

- 功能完成并合并后，及时删除对应的`feature`分支
- 版本发布完成后，及时删除对应的`release`分支
- 紧急修复完成并合并后，及时删除对应的`hotfix`分支

## 四、版本管理

### 1. 版本号规则

采用语义化版本号（Semantic Versioning）：`MAJOR.MINOR.PATCH`

- **MAJOR**：主版本号，当进行不兼容的API更改时递增
- **MINOR**：次版本号，当添加新功能且向下兼容时递增
- **PATCH**：修订号，当进行向下兼容的bug修复时递增

### 2. 版本发布流程

1. 从`develop`分支创建`release/vX.Y.Z`分支
2. 在`release`分支上进行版本号更新和最终测试
3. 测试通过后，将`release`分支合并到`master`分支
4. 在`master`分支上打标签：`git tag vX.Y.Z`
5. 将标签推送到远程仓库：`git push --tags`
6. 将`release`分支合并回`develop`分支
7. 删除`release`分支

## 五、代码审查规范

### 1. 审查内容

- 代码正确性和完整性
- 代码风格和可读性
- 性能和安全性考虑
- 测试覆盖情况

### 2. 审查流程

1. 创建Pull Request并指派审查人员
2. 审查人员进行代码审查并提出意见
3. 开发者根据意见修改代码
4. 审查通过后，由审查人员或项目经理合并代码

## 六、冲突解决

- 定期从上游分支（`develop`或`master`）拉取最新代码，减少冲突
- 冲突发生时，与相关开发人员协商解决
- 确保解决冲突后的代码可正常编译和运行

## 七、附则

- 本规范自发布之日起生效
- 规范将根据项目实际情况进行调整和完善
- 所有团队成员必须严格遵守本规范
